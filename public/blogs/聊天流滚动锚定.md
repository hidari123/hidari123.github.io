# 聊天流的滚动锚定：流式回复期间为什么不能跟着滚

聊天界面最古老的体验问题之一：**流式回复时，内容在底部不断生长，用户往回翻历史时，自动滚动把人一次次拽回底部。**

它看起来是小事，实际是"用户能不能在 AI 说话时干正事"的问题——用户想在长回复流式输出时回看上面的内容，被拽三次就放弃了。

AtomOS 的实现把这个交互拆得很细，注释里全是踩坑记录。

## 一、核心状态：一个 ref，不是 state

```typescript
const userScrollRef = useRef(false);
const atBottomRef = useRef(true);
```

两个关键状态都是 **ref 而不是 state**——它们不驱动渲染，只被滚动事件读写。每次 scroll 事件都 setState 会把滚动处理变成渲染风暴。

`userScrollRef` 的语义：**"用户是否有向上滚的意图"**。它不是"当前是否在底部"——底部状态另有 `atBottomRef`——而是**意图标记**：一旦用户表达了"我要往上"，自动跟随就该停。

## 二、意图判别：哪些事件才算"用户想滚"

这是整个设计最细的部分。直接监听 scroll 事件是错的——**scroll 事件不一定来自用户**：

- 程序自己的 `scrollTo` 会触发 scroll 事件
- 内容生长导致 scrollHeight 变化，视口"相对"移动
- 键盘翻页、锚点跳转、外设……

AtomOS 只认两种真实手势：

**滚轮/触摸板在滚动容器上的滚动**——通过监听容器本身的 scroll 事件序列判别（后述）。

**鼠标按在滚动条上拖动**：

```typescript
// A mousedown on the transcript is only scroll intent when it lands on
// the scroll container itself — i.e. the scrollbar. Clicks on a bubble, a link or a
// "Thinking" disclosure target a descendant, and treating those as scrolling
// would drop the follow while the user is just interacting with the message.
const onThreadMouseDown = useCallback((e: React.MouseEvent) => {
  if (e.target === threadRef.current) userScrollRef.current = true;
}, []);
```

判据是 `e.target === threadRef.current`——**事件目标必须是滚动容器本身，不能是它的子元素**。点气泡、点链接、展开"思考过程"折叠块，target 都是后代元素，不算滚动意图。只有点在滚动条（容器自身、无子元素的命中区域）才算法意图。

## 三、最狠的坑：smooth scrollTo 的自我污染

自动跟随底部的实现是：

```typescript
el.scrollTo({ top: el.scrollHeight, behavior: "smooth" });
```

但平滑滚动是**异步动画**——它在几百毫秒里持续触发 scroll 事件。这些 scroll 事件的 scrollTop 是动画中间值，**看起来和"用户在往上滚"一模一样**。

注释把这个坑写得明明白白：

```typescript
// Only a real input gesture may break the "follow the bottom" stickiness. Our
// own smooth scrollTo emits scroll events for the whole length of its
// animation, and while it is mid-flight the thread genuinely IS away from the
// bottom — reading that as the user scrolling up would drop the follow and
// raise the pill in the middle of a reply the user is watching.
```

如果把自己动画的中间状态误判为用户滚动，会发生：**自动跟随启动 → 动画的 scroll 事件被误判为用户意图 → 跟随被取消 → "有新内容"的提示药丸在用户眼前弹出**——用户根本没碰任何东西，界面却自己乱了。

解法有两层。

**第一层：意图标记由手势设置，scroll 事件只消费**：

```typescript
const onThreadScroll = useCallback(() => {
  const el = threadRef.current;
  if (!el) return;
  const atBottom = el.scrollHeight - el.scrollTop - el.clientHeight < BOTTOM_SLACK;
  if (atBottom) {
    atBottomRef.current = true;
    userScrollRef.current = false; // caught up — the next gesture starts fresh
    setNewBelow(false); // retire the pill
  } else if (userScrollRef.current) {
    atBottomRef.current = false;
  }
}, [id]);
```

scroll 处理器的逻辑：滚到底部 → 恢复跟随、清意图、撤药丸；**不在底部时，只有 `userScrollRef.current === true`（已有手势意图）才取消跟随**——自己动画产生的"不在底部"因为从未设置过意图标记，取消不了任何东西。

**第二层：re-pin 时清意图**：

```typescript
// Re-pin to the live end. Clears the gesture flag too: the smooth scroll this
// precedes emits scroll events from a position that is not yet the bottom, and
// with the flag still set those would immediately un-pin us again.
const pinToBottom = useCallback(() => {
  atBottomRef.current = true;
  userScrollRef.current = false;
  setNewBelow(false);
}, []);
```

手动回底（点药丸）时**先清标记再启动滚动**——新动画产生的 scroll 事件看到的是"无意图"，不会再误判。

## 四、药丸（pill）：不打断，只提示

用户翻上去后，流式输出继续。此时不打断（不滚动），但要在**不打扰的位置**提示"下面有新内容"：

```typescript
const jumpToBottom = useCallback(() => {
  const el = threadRef.current;
  if (!el) return;
  pinToBottom();
  el.scrollTo({ top: el.scrollHeight, behavior: "smooth" });
}, [pinToBottom]);
```

药丸是个按钮，点击 = `pinToBottom` + 平滑滚到底。`pinToBottom` 先重置状态再滚动，保证动画期间的状态一致。

## 五、会话切换：scrollCache 与"瞬时定位"

切回一个看过的会话，应该**回到上次离开的滚动位置**——AtomOS 用 `scrollCache`（session id → scrollTop 的 Map）记住每个会话的位置。

而恢复定位有个专门的坑，注释也不含糊：

```typescript
// Always an instant assignment, never an animated scrollTo: smooth-scrolling
// a freshly painted transcript is exactly the whole-history fly-by that made
// a tab round-trip look like the session reloading.
el.scrollTo({ top, behavior: "instant" });
```

**恢复必须用 `behavior: "instant"`**。如果用平滑滚动，用户会看到整段历史从旧位置"飞"到新位置——切换会话看起来像重新加载了整个会话，焦虑感直接拉满。

还有一层：CSS 里的 `scroll-behavior: smooth` **会传染给普通的 `scrollTop =` 赋值**。注释里特别标注：

```typescript
// behavior:"instant" is load-bearing, not a default spelled out. `.thread`
// carries `scroll-behavior: smooth` in CSS, which applies to a plain
// `scrollTop =` assignment too — so without this the placement animates and
// the whole-history fly-by is back.
```

**`behavior: "instant"` 是承重的**——不加它，CSS 的 smooth 会接管，飞掠动画卷土重来。

## 六、为什么这个话题值得单开一篇

因为它是 **"看似简单的交互，深挖全是坑"** 的标本：

| 层 | 坑 | 解法 |
|---|---|---|
| 事件 | scroll 事件不等于用户意图 | 手势设标记，scroll 只消费 |
| 事件 | smooth 动画的中间态像用户滚动 | 标记由手势独占设置权 |
| 判定 | mousedown 落点区分滚动条/内容 | `target === container` 判据 |
| 恢复 | 会话切换的定位像"重新加载" | `instant` + 记忆位置 |
| CSS | `scroll-behavior: smooth` 传染赋值 | 显式 `behavior: "instant"` |

每一行注释都是一次真实的体验事故。这种代码没法靠"想清楚再写"一次写对，只能靠对着用户行为一轮轮磨。

## 七、总结

1. **意图（ref）与状态（atBottom）分离**，滚动事件只消费意图不产生意图
2. **手势的独占设置权**：自己动画的 scroll 事件永远改不了意图标记
3. **mousedown 判据用事件 target**，滚动条命中 = 容器自身
4. **恢复定位用 instant**，`scroll-behavior: smooth` 的传染性要显式压制
5. **不打断 + 药丸提示**：流式期间用户的阅读优先级高于"最新内容"

一句话：**自动滚动的前提是能正确回答"这次滚动是谁的意思"——把动画自己产生的事件和用户手势区分开，是全部问题的核心。**
