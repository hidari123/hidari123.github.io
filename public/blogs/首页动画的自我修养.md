# 前端首页动画的自我修养：性能、可访问性与克制

AtomOS 首页有个分子网络粒子背景——原子（带元素符号 C/N/O/H/S/P）、化学键连线、鼠标吸引。这个动画迭代了 5 个版本（v3.5 到 v3.5f），每次改动都有完整的 git 记录和验证截图。

它是个小东西，但**注释密度是全仓库最高的之一**——每一行防御都对应一次真实翻车。这篇讲取舍。

## 一、实现：轻量 Canvas，不是 WebGL

```typescript
interface Node {
  bx: number; by: number; // base drift position
  x: number; y: number;   // rendered position (base + sine wobble)
  vx: number; vy: number;
  r: number;
  phase: number;          // per-node sine phase for organic drift
  el?: string; shell: number; // element symbol + orbit shell count
}
```

数据模型很朴素：每个节点有**基准位置**（`bx/by`）和**渲染位置**（`x/y` = 基准 + 正弦摆动）。正弦相位每节点独立——漂移看起来"有机"而不是整体平移。

技术选型是 2D Canvas 而非 WebGL/WASM：**几十个节点的连线渲染，Canvas 2D 绰绰有余**，WebGL 的收益要在几千粒子时才体现。选型的克制和"够用就好"在这里体现得很清楚。

帧率目标是注释里明写的：`~30fps`——不是 60。**装饰性动画的帧率预算低于交互动画**，30fps 对背景漂移足够顺滑，CPU 占用减半。

## 二、v3.5f 之前的教训：reduced-motion 的过度纠正

最值得写的是 v3.5d-v3.5f 这三个版本的迭代，git log 里的记录：

```
v3.5d — reduced-motion no longer kills all entrances
       （reduced-motion 不再杀死所有入场动画）
v3.5e — stop strobing loops under reduced-motion
       （reduced-motion 下停止频闪式循环——stop, don't compress）
v3.5f — loops slowed site-wide, reduced-motion unfreezes them
       （循环全站减速；reduced-motion 解冻它们）
```

串起来读是一个完整的认知修正过程：

**第一版（< v3.5d）**：`prefers-reduced-motion` 一刀切——全部动画冻结。**这是过度服从**：前庭障碍用户需要避免的是**大幅运动和视差**，不是"任何像素变化"。一刀切把界面的"生命感"也杀死了。

**v3.5d**：修正"入场动画全灭"——入场是短暂、一次性的，不在前庭问题的主要射程内。

**v3.5e**：发现"压缩"不对——循环动画在 reduced-motion 下被做了压缩处理（比如缩短周期），结果产生**频闪**。注释里的结论一针见血：`stop, don't compress`——**该停就停，压缩比停止更糟**（缩短周期 = 加快闪烁 = 恰好制造了要避免的问题）。

**v3.5f（当前）**：最终立场——

```typescript
// Motion-respect (v3.5f): the slow ambient drift keeps running under
// prefers-reduced-motion — freeze was over-correction.
```

**慢速环境漂移保留，冻结是过度纠正。** 漂移的正弦幅度小、速度慢（每秒几像素），不构成前庭刺激；而冻结让首页变成一张死图，牺牲了所有用户的产品气质。

这条演进线的价值在于：**可访问性不是"减法教条"，是对"什么构成伤害"的精确理解**。频闪（快、重复、高对比）伤人，慢漂移不伤——判据是运动特征，不是"有/无"。

## 三、离屏暂停：IntersectionObserver

```typescript
// Pauses when off-screen via IntersectionObserver. ~30fps.
```

不可见就停——和 `usePollWhenVisible`（轮询那篇）同一哲学：**没人看的渲染一帧都不该跑**。IntersectionObserver 不像 scroll 监听那样高频触发，进出视口各回调一次，开销几乎为零。

## 四、pointer-events 的代理方案

首页背景铺在 Canvas 上，注释里有个不起眼但很实际的决策：

```typescript
// Pointer: the hero canvas is CSS `pointer-events: none` (page content must
// stay clickable), so mouse tracking listens on the canvas's PARENT
// element instead — the event target that actually receives the pointer.
```

两层拆解：

1. Canvas 本身 `pointer-events: none`——**背景不能挡住页面内容的点击**。背景图挡住按钮是最蠢也最常见的 bug
2. 但鼠标吸引效果需要鼠标坐标——监听挪到**父元素**上（真正接收指针事件的层）

把"视觉层"和"交互层"分开：视觉上 Canvas 在最底，事件上父容器代收。这个手法在任何"背景特效"场景都通用。

## 五、元素细节：科学气质是设计出来的

粒子的美术设定带着领域特征：

```typescript
const ELEMENTS = ["C", "N", "O", "H", "S", "P"];
```

- 原子显示**元素符号**（碳氮氧氢硫磷——生命的六大元素）
- 近距离画**双键平行线**，远距离画单键细线——化学键的真实画法
- 部分原子带**轨道环**（`shell` 数）

这不是"随机粒子+连线"的通用背景，是**领域语言的视觉表达**。生物计算平台的首页用化学键语言说话，用户第一眼的"这是给我做的工具"感觉就来自这些细节。

## 六、性能账

全链路加起来：

| 手段 | 收益 |
|---|---|
| 30fps 而非 60 | CPU 减半，装饰动画够用 |
| 离屏暂停（IntersectionObserver） | 不可见零开销 |
| 2D Canvas 而非 WebGL | 实现简单，几十节点无压力 |
| 慢速正弦漂移而非物理模拟 | 无累积误差，无需积分 |
| reduced-motion 保留慢漂移 | 无障碍合规且不死板 |

首页动画的"自我修养"就这几条：**帧率预算要低、不可见要停、事件要代理、无障碍要精确**。

## 七、总结

1. **装饰动画 30fps 足够**，帧率预算让位给交互
2. **reduced-motion 的正确姿势是"stop, don't compress"**——该停的停（频闪），该留的留（慢漂移），判据是运动特征不是存在本身
3. **离屏暂停**：IntersectionObserver，零成本
4. **pointer-events 代理**：视觉层与交互层分离
5. **领域美术**：元素符号、双键画法——背景也在说领域语言

一句话：**背景动画的品质不在多炫，在于每个"不跑"的时刻都有明确理由——看不见不跑、伤人不跑、该慢不赶。**
