# 前端性能优化实战：从 FPS 监控到首屏瘦身

性能优化这件事有个反直觉的特点：**你最想优化的部分，往往不是你真正的问题所在**。

我见过太多这样的项目：开发者凭感觉觉得"页面好卡"，然后花一周做虚拟列表、加 memo、节流防抖——改完发现没什么变化。真正的原因可能是首屏加载了 1.1MB 的 JS，或者一张 2MB 未压缩的图片。

**优化的第一步永远是测量，不是猜测。** 这篇文章记录我在一个真实 AI 博客项目（`hidari123.github.io`）上的完整优化流程，包括最后实测的构建产物数据。

## 一、先自建监控，而不是先优化

项目里有个性能监控面板，但它不是用第三方库，而是自己写的。原因很简单：我要监控的指标很特殊，尤其是"AI 调用统计"这种业务维度的东西，第三方工具采集不到。

核心 hook 大约两百行，我挑关键部分讲。

### 1.1 FPS：用 rAF 而不是定时器

最直觉的写法是 `setInterval` 每秒算一次。但这个测不准，因为它测的是"定时器触发频率"，不是"真实渲染帧率"。

正确做法是用 `requestAnimationFrame` 逐帧计数：

```typescript
const calculateFPS = useCallback(() => {
  const now = performance.now();
  const delta = now - lastTimeRef.current;

  frameCountRef.current++;

  if (delta >= 1000) {
    fpsRef.current = Math.round((frameCountRef.current * 1000) / delta);
    frameCountRef.current = 0;
    lastTimeRef.current = now;
  }

  animationFrameRef.current = requestAnimationFrame(calculateFPS);
}, []);

useEffect(() => {
  animationFrameRef.current = requestAnimationFrame(calculateFPS);
  return () => {
    if (animationFrameRef.current) {
      cancelAnimationFrame(animationFrameRef.current);
    }
  };
}, [calculateFPS]);
```

关键点：
- **rAF 和渲染管线同步**，浏览器每次绘制前才回调，测出来的就是真实帧率
- 计数器放在 `ref` 里而不是 `state`——每秒更新一次 state 就够了，逐帧更新 state 会自己造成性能问题
- 记得在 cleanup 里 `cancelAnimationFrame`，否则组件卸载后循环会一直跑

### 1.2 重绘次数：PerformanceObserver

"重绘次数"用的是 `layout-shift`（布局偏移）和 `paint`（绘制）条目：

```typescript
observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.entryType === 'layout-shift' || entry.entryType === 'paint') {
      repaintCountRef.current++;
    }
  }
});

observer.observe({ entryTypes: ['layout-shift', 'paint'] });
```

这里有个值得注意的设计取舍：**累计值而非速率**。因为我想知道的是"打开页面至今一共重绘了多少次"，这比"每秒重绘几次"更能反映整体健康度——一个页面如果总重绘 500 次，值得警惕。

`try-catch` 包住 observer 创建是必要的：`PerformanceObserver` 的 `entryTypes` 支持情况在不同浏览器有差异，直接抛错会让整个 hook 崩掉。

### 1.3 内存：Chrome 专属 API

```typescript
interface PerformanceMemory {
  jsHeapSizeLimit: number;
  totalJSHeapSize: number;
  usedJSHeapSize: number;
}
```

注意这是 **Chrome 独有的非标准 API**，其他浏览器返回 `undefined`。所以代码里必须有降级：

```typescript
const getMemoryUsage = useCallback((): { used: number; limit: number } => {
  const memory = (performance as PerformanceWithMemory).memory;
  if (memory) {
    return { used: memory.usedJSHeapSize, limit: memory.jsHeapSizeLimit };
  }
  return { used: 0, limit: 0 };   // 优雅降级
}, []);
```

UI 层也要对应处理——`metrics.memoryLimit > 0` 时才显示上限，否则显示 "Chrome Only"。

**这种"非标准 API 必须有降级路径"的意识，比 API 本身更重要。**

### 1.4 一个有意思的细节：检测 DevTools 是否打开

面板只在开发模式或 DevTools 打开时显示，节省生产环境的性能开销：

```typescript
const isDevToolsOpen = (): boolean => {
  const threshold = 160;
  const widthThreshold = window.outerWidth - window.innerWidth > threshold;
  const heightThreshold = window.outerHeight - window.innerHeight > threshold;
  return widthThreshold || heightThreshold;
};
```

原理：DevTools 打开时会在窗口外占用空间，导致 `outerWidth` 和 `innerWidth` 出现差值。

这是个偏 hack 的技巧，跨浏览器不可靠（DevTools 停靠在同一窗口内时不产生差值），但作为开发期辅助够用了。

### 1.5 面板组件的性能细节

面板本身也做了优化，虽然组件不大，但几个手法值得记：

```typescript
const MetricItem = memo<MetricItemProps>(({ icon, label, value, subValue, color }) => (
  // ...
));
MetricItem.displayName = MetricItem;
```

- `memo` 包裹每个指标项，避免父组件每秒更新时所有项都重渲染
- 显式写 `displayName`——否则 React DevTools 里只能看到一堆 `Memo` 或匿名组件，调试时抓瞎
- 拖拽逻辑用 `useRef` 存起始位置，用 `useState` 存当前位置。移动过程中不 setState 只改 ref，松手时才 setState 落定——**避免拖拽过程中触发几十次渲染**

最后这条其实是这里最重要的优化：拖拽是高频操作，如果 mousemove 每次都 setState，会造成明显卡顿。

## 二、监控建好之后，看见了什么

面板建好跑起来，暴露出来的问题是：**首屏 JS 体积过大**。

Vite 构建时的告警很直白：

```
(!) Some chunks are larger than 500 kB after minification.
dist/assets/index-Cgr89g3h.js   1,116.62 kB │ gzip: 333.56 kB
```

单个主 chunk 1.1MB（gzip 后 333KB）。对一个**博客**来说，这个数字荒谬——博客的主体是 Markdown 文章，几 KB 就够。

原因很清楚：这个项目同时塞进了三个重的东西：

1. **React + framer-motion** —— 动画库本身不小
2. **onnxruntime-web** —— 浏览器端跑机器学习模型的运行时
3. **KaTeX / Markdown 渲染链路** —— 文档渲染

问题在于：**它们全都被打进了首屏主 chunk**。哪怕用户只是来读一篇文章，浏览器也要先下载解析整个 1.1MB。

## 三、优化：让重的模块按需加载

思路很直接——**不用的东西不该在首屏**。

### 3.1 手动分包

```typescript
build: {
  target: 'esnext',
  rollupOptions: {
    output: {
      manualChunks: {
        // 把体积大、且相对独立的依赖拆出来
        react: ['react', 'react-dom'],
        motion: ['framer-motion'],
        markdown: ['react-markdown', 'remark-gfm', 'remark-frontmatter'],
        ml: ['onnxruntime-web'],
      },
    },
  },
},
```

拆包之后，浏览器可以**并行下载**这些 chunk，而不是等一个巨大的文件。同时因为分包，浏览器缓存的粒度变细——改了文章内容不会让整个 1.1MB 全部失效重下。

### 3.2 动态导入：把"功能"和"首屏"解耦

分包只解决了并行下载，没解决"这个功能用户到底用不用"。真正的解法是动态导入（代码分割）。

比如浏览器端 RAG 功能，只有用户真的点了"AI 问答"才需要加载：

```typescript
// 不用时完全不加载
const ragService = await import('@/services/ragService');
```

用 `import()` 语法。Vite 会自动把动态导入的模块拆成独立的 chunk，只在调用时才请求。

**这个改动的收益是结构性的**：一个只用来看文章的访客，下载量从 1.1MB 降到了可能不到 300KB。

### 3.3 依赖本身也要特殊处理

`onnxruntime-web` 这种 WASM 依赖有专门的坑，我在 `vite.config.ts` 里做了两件事：

```typescript
optimizeDeps: {
  exclude: ['onnxruntime-web'],
},
```

排除预构建——否则 Vite 的依赖预打包会把 WASM 搞坏。

还有跨源隔离的响应头，因为 onnxruntime 的多线程模式需要 `SharedArrayBuffer`，而它只在跨源隔离环境下可用：

```typescript
server: {
  headers: {
    'Cross-Origin-Opener-Policy': 'same-origin',
    'Cross-Origin-Embedder-Policy': 'require-corp',
  },
},
```

**这两个 header 在生产环境也要配**。如果部署时漏了，浏览器端多线程推理会静默降级成单线程，性能可能慢好几倍——而且不会有任何报错，只会"感觉有点慢"。这类"静默降级"是最难查的坑。

## 四、WASM 资源的治理

构建产物里还有这么一行：

```
dist/assets/ort-wasm-simd-threaded.jsep-MDYUKy93.wasm   28,312.03 kB
```

**27.6MB 的 WASM 文件。**

这个文件是 onnxruntime 的推理内核。不管用户用不用 AI 功能，它现在都被打进了产物。

处理方式有两个层次：

**短期**：确保它不被首屏加载（靠上面的动态导入）。这样它变成一个"用到了才下载"的资源。

**长期**：这个体积对博客站点来说是过重的。一个更合理的架构是——把 AI 相关能力（模型 + 运行时）拆到独立的部署单元，主博客只保留内容渲染。这样两边的用户互不影响：

- 读博客的人：几百 KB，秒开
- 用 AI 功能的人：按需下载模型，且不影响首屏

这也是我之前提到的"多模态缓存"话题的延伸——模型文件本身就是最大的那类需要缓存的资源。

## 五、构建产物验证

优化之后的实测数据（`dist/` 目录）：

| 资源 | 体积 | gzip 后 |
|---|---|---|
| `index.html` | 0.73 KB | 0.54 KB |
| `index-*.js`（主包） | 1,116.62 KB | 333.56 KB |
| `index-*.css` | 69.38 KB | 12.42 KB |
| `giscus-*.js` | 25.49 KB | 8.93 KB |
| WASM 运行时 | 28,312.03 KB | — |

**注意 giscus 已经被拆成独立 chunk 了**——评论系统是典型的"首屏不需要"功能，它被正确地隔离出去了。这就是分包该有的样子。

这里我要诚实说明：**主包 1.1MB 在这次优化后仍然偏大**。真正的拆分（按功能动态导入 AI 模块）还需要进一步做。上面这个表格是中间状态，不是终点。

把"未完成"写出来比只报喜更有用——这才是真实的优化过程。

## 六、一条容易被忽略的工程细节

优化过程中我踩到一个和性能无关但很影响效率的坑：**构建脚本里的一个分号**。

```json
"build": "npm run tsc; npm run vite-build"     // ❌
"build": "npm run tsc && npm run vite-build"   // ✅
```

`;` 和 `&&` 在这里差别是致命的。npm 把 `tsc;` 当成**脚本名**的一部分去查找（报错信息是 `Missing script: "tsc;"`），整个构建直接失败。

更有意思的是，它还**伪装成功**了：`vite-plugin-gh-pages` 会在构建末尾尝试推送 dist，但它是从一个临时 clone 里推送的，推送失败被静默吞掉。所以日志上写着"Published to gh-pages"，实际上远端分支根本没更新。

**教训：CI 里千万别让"部署成功"变成一个只靠日志判断的事。** 要么去掉那个插件用 `npm run deploy`（可靠，失败会报错），要么上 GitHub Actions（部署状态直接显示在 commit 上）。

## 七、优化清单

按收益排序，我在这个项目上的完整建议：

| 优先级 | 措施 | 预期收益 |
|---|---|---|
| P0 | 动态导入 AI / RAG 模块 | 首屏 JS 减少 50%+ |
| P0 | 去掉假成功的部署插件 | 消除"以为部署了其实没有" |
| P1 | `manualChunks` 拆分大依赖 | 并行下载 + 缓存粒度变细 |
| P1 | WASM 移出主产物 | 产物从 27MB+ 降到 MB 级 |
| P2 | 图片资源现代化（WebP/AVIF） | 视图片占比而定 |
| P2 | 生产环境配 COOP/COEP | 恢复 WASM 多线程 |
| P3 | 虚拟列表（如果有大列表页） | 长列表滚动流畅度 |

## 结语

性能优化最容易走偏的地方，是**先动手后测量**。我这个项目一开始如果直接上 memo、虚拟列表、节流防抖，能改的都改了，但主包还是 1.1MB——因为真正的瓶颈压根不在那里。

正确的顺序是：

1. **建监控**（哪怕只是个两百行的自建面板）
2. **跑数据**（看到 1.1MB 这个事实）
3. **找结构**（什么问题导致 1.1MB？→ 全都进了首屏）
4. **改结构**（动态导入解耦）
5. **再验证**

第 2 步和第 4 步之间的那个"发现问题"的动作，是整个流程里最值钱的部分。工具和技巧都是次要的——**没有测量，所有优化都是猜。**
