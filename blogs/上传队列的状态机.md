# 上传队列的状态机：一个 hook 管好并发、取消、重试和冲突

上传一个文件很容易。上传队列很难——因为用户会：

- 一次拖 20 个文件进来
- 上传中途取消
- 某个失败了要重试
- 关闭页面（要中止）
- 重试时又拖了新文件进来

这些操作交错在一起，就要求一套严谨的状态管理。AtomOS 的 `useWorkspaceUpload.ts` 是个 110 行的完整实现。

## 一、状态定义：一个可失败、可取消、可冲突的上传

```typescript
export type WorkspaceUploadState = {
  file: File;
  path: string;
  controller: WorkspaceUpload;
  progress: WorkspaceUploadProgress;
  status: "uploading" | "failed" | "conflict";
  error?: string;
};
```

三个状态值不是随便起的：

- `uploading` —— 进行中
- `failed` —— 失败（网络错误、服务端 5xx），**可以重试**
- `conflict` —— **服务端返回 409**，语义是"文件已存在/校验和不匹配"，**重试没用，用户得做决定**

把 conflict 从 failed 里拆出来，是因为它们的 UI 表达完全不同：failed 显示"重试"按钮，conflict 显示"覆盖/跳过"选项。合成一个状态就要在 UI 层做二次判断，而判断逻辑写在类型里更可靠。

## 二、双轨状态：state 管 UI，ref 管身份

这是整个实现的核心模式：

```typescript
const [upload, setUpload] = useState<WorkspaceUploadState | null>(null);
const activeRef = useRef<WorkspaceUploadState | null>(null);
const queueRef = useRef<{ file: File; path: string }[]>([]);
```

三个容器，两个轨道：

| 容器 | 类型 | 用途 |
|---|---|---|
| `upload` | state | **驱动渲染**，UI 显示什么 |
| `activeRef` | ref | **身份校验**，这个回调是不是当前上传的 |
| `queueRef` | ref | **可变队列**，不需要渲染的待传列表 |

为什么需要 `activeRef`？看这段：

```typescript
let controller: WorkspaceUpload;
controller = uploadProjectWorkspaceFile(projectId, normalizedPath, file, (progress) => {
  setUpload((current) => current?.controller === controller ? { ...current, progress } : current);
});
```

注意 `let controller` 然后 `controller = ...`——因为要在回调里引用 controller 本身（对比身份），而 controller 是 upload 函数返回的。ES 的 TDZ（暂时性死区）不允许在 `const` 声明前引用，所以用 `let` 先声明再赋值。

**每次上传有唯一身份（controller 对象），所有回调先验身份再更新状态**：

```typescript
void controller.promise.then(async (result) => {
  if (activeRef.current?.controller !== controller) return;   // ← 身份闸门
  activeRef.current = null;
  setUpload(null);
  await onComplete?.(result);
  runNext();
})
```

这个闸门防的是什么？**过期回调污染当前状态**。场景：

1. 上传 A 启动
2. 用户取消 A，`activeRef` 被清空
3. A 的 promise 稍后 reject（AbortError 也是异步传播的）
4. 用户已经重试了 A'，`activeRef` 现在指向 A'
5. 如果 A 的回调不验身份，会把 A' 的 UI 状态覆盖成"A 失败了"

进度回调里的 `setUpload((current) => current?.controller === controller ? ... : current)` 是同样的防御——**函数式 setState + 身份比对**，避免闭包读到过期的 state。

## 三、串行队列：一个一个传

```typescript
const runNext = useCallback(() => {
  const next = queueRef.current.shift();
  setQueued(queueRef.current.length);
  if (!next) return;
  start(next.file, next.path);
}, []);
```

`shift()` 取出一个并从队列移除，`setQueued` 更新待传计数。

**串行而非并行**是有意的：并行上传 20 个 5 GiB 文件会打满带宽，用户体验反而更差（每个都慢）。串行下第一个秒传完，用户立刻看到成果，队列在后台推进。

enqueue 的守卫：

```typescript
const enqueue = useCallback((items: { file: File; path: string }[]) => {
  if (!projectId || items.length === 0) return;
  const oversized = items.find((item) => item.file.size > MAX_PROJECT_FILE_BYTES);
  if (oversized) {
    onError?.(new Error("file exceeds the 5 GiB upload limit"));
    return;
  }
  queueRef.current.push(...items);
  setQueued(queueRef.current.length);
  if (!activeRef.current) {
    runNext();
  }
}, [...]);
```

**整个批次先校验大小，超标就一个都不收**——而不是收下 19 个、拒绝 1 个。批量操作里，"要么全做要么不做"比"部分成功"更可预期。

末尾的 `if (!activeRef.current) runNext()`：**只有没有活跃上传时才启动队列**。有活跃上传时它自己完成后会调 `runNext`，不用重复启动。

## 四、取消的分层处理

```typescript
const cancel = useCallback(() => {
  activeRef.current?.controller.cancel();
}, []);

const cancelAll = useCallback(() => {
  queueRef.current = [];
  setQueued(0);
  activeRef.current?.controller.cancel();
}, []);
```

**取消当前** vs **取消全部**——两个 API 都要有。用户在上传一个文件时点叉，期望是"停这一个"；拖了 20 个然后想全停，需要另一个入口。

AbortError 的特殊处理：

```typescript
.catch((error: unknown) => {
  if (activeRef.current?.controller !== controller) return;
  if (error instanceof DOMException && error.name === "AbortError") {
    activeRef.current = null;
    setUpload(null);
    runNext();     // ← 取消也要推进队列
    return;
  }
  // ...
});
```

**取消不是失败**。取消后要清状态并继续下一个——如果取消会卡住队列，用户取消一个就得手动重试剩下的 19 个，很糟。

而真正的失败**停队列**：

```typescript
const failed = { ...state, status: error instanceof WorkspaceUploadError && error.status === 409 ? "conflict" as const : "failed" as const, error: String(error) };
activeRef.current = failed;
setUpload(failed);
onError?.(error);
// A failed upload halts the queue; the user decides (retry or cancel).
```

注释点明设计立场：`the user decides`。失败后不自动继续——**如果是路径冲突（409），自动继续传后面的文件会产生"传了一半"的混乱状态**。让用户决定是重试、跳过还是取消。

## 五、重试：复用同一个 File 对象

```typescript
const retry = useCallback(() => {
  const failed = activeRef.current;
  if (failed?.status === "failed" || failed?.status === "conflict") start(failed.file, failed.path);
}, [start]);
```

重试直接 `start(failed.file, ...)`——`File` 对象还在内存里（用户选的原始文件），不需要用户重新拖一遍。

注意状态守卫：`status === "failed" || status === "conflict"`——**只有这两种状态可重试**，`uploading` 状态重试会启动重复上传。

## 六、路径规范化在上传边界

```typescript
const normalizedPath = path.replace(/^\/+/, "");
```

拖拽上传的路径来自 `DataTransferItem.webkitRelativePath` 或 `file.name`，可能带前导斜杠。去掉前导 `/` 让路径和后端约定一致（`/workspace/xxx` 由后端补全）。

**这行很轻但必要**——前导斜杠在后端可能构成绝对路径逃逸，虽然后端还有白名单校验（那篇讲过），但客户端不该传已经知道有问题的路径。

## 七、上限校验的双位置

`enqueue` 里校验整批，`start` 里再校验单个：

```typescript
const start = useCallback((file: File, path: string) => {
  if (!projectId) return;
  if (file.size > MAX_PROJECT_FILE_BYTES) {
    const error = new Error("file exceeds the 5 GiB upload limit");
    onError?.(error);
    return;
  }
```

为什么重复？因为 `start` 有两个入口：`runNext`（来自队列）和 `retry`（直接重试）。重试的文件虽然当初已经校验过，但 `start` 是独立的执行路径——**防御性校验放在最靠近执行的地方**。

这是个好习惯：不要假设"调用方已经检查过了"。

## 八、Hook 契约：UI 挂载点和工具函数分开

```typescript
return { upload, queued, start, enqueue, cancel, cancelAll, retry };
```

返回两个**状态**（`upload`、`queued`）+ 五个**命令**。职责分离清晰：

- 状态：读
- 命令：写

同时这个 hook 被**两个组件共用**——Workspace 页面和聊天输入框的拖放区。共享逻辑（队列、进度、取消）不重复实现，两处的 UI 表现可以不同（Workspace 显示详细进度条，输入框显示紧凑计数）。

docstring 说明了这一点：

```typescript
/**
 * Shared upload lifecycle for Workspace and composer drop targets.
 *
 * Supports a serial queue: `enqueue` appends files and uploads them one at a
 * time (each upload starts only after the previous settles). The visible
 * state is the active upload plus the pending count.
 */
```

**"visible state is the active upload plus the pending count"** —— 明确定义了渲染契约：UI 只需要知道"当前传什么"和"还剩几个"，不需要维护完整队列。

## 九、总结

1. **ref 管身份，state 管渲染**：controller 对象做身份令牌，所有回调先验身份
2. **串行队列**：一次一个，避免并行打满带宽
3. **取消 ≠ 失败**：取消推进队列，失败停队列等用户决定
4. **409 conflict 独立状态**：UI 表达不同（覆盖/跳过 vs 重试）
5. **重试复用 File 对象**：不用让用户重拖
6. **上限校验双位置**：`enqueue` 批量拦 + `start` 执行前拦
7. **返回状态和命令分离**：hook 契约清晰，可被多处复用

一句话：**异步队列的难度不在"怎么传"，在"过期的回调怎么不污染当前状态"——给每次操作一个身份令牌，所有回调先验明正身。**
