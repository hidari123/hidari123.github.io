# 文件类型分派的四层兜底：为什么 mime 永远排在扩展名前面

工作区的文件预览要回答一个问题：**这个文件该用什么渲染器打开？**

看起来是个 if-else，实际是四种冲突来源的仲裁：

1. **扩展名**会骗人——`data.csv` 可能是 JSON
2. **mime** 会缺失——浏览器上传的 `File` 对象对很多类型给不出 mime
3. **内容嗅探** 最准但最贵——要读文件
4. **用户意图**（右键"以代码打开"）要能覆盖前三者

AtomOS 的 `rendererRegistry.ts` 是这个仲裁的实现，只有 40 行，但每个分支的顺序都有理由。

## 一、判定顺序：mime → 扩展名 → 嗅探

```typescript
const sequenceExtensions = new Set(["fa", "fasta", "faa", "fna", "a3m", "aln"]);
const structureExtensions = new Set(["cif", "mmcif", "pdb"]);
const molstarSceneExtensions = new Set(["mvsj"]);
const imageExtensions = new Set(["png", "jpg", "jpeg", "gif", "svg", "webp", "bmp", "ico"]);

export function rendererKindFor(metadata: PreviewMetadata, sniff = ""): RendererKind {
  const ext = metadata.name.split(".").pop()?.toLowerCase() ?? "";
  const mime = metadata.mime?.split(";", 1)[0].toLowerCase();
  if (mime === "text/markdown" || ext === "md" || ext === "markdown") return "markdown";
  if (mime === "text/csv" || mime === "text/tab-separated-values" || ext === "csv" || ext === "tsv") return "table";
  if (mime?.startsWith("image/") || imageExtensions.has(ext)) return "image";
  if (mime === "application/pdf" || ext === "pdf") return "pdf";
  if (molstarSceneExtensions.has(ext) || mime === "application/vnd.molstar.mvsj+json") return "molstar_scene";
  if (structureExtensions.has(ext) || /^(data_)?(entry|atom_site|struct)_/mu.test(sniff)) return "structure";
  if (sequenceExtensions.has(ext) || /^>[^\n]*/u.test(sniff.trim())) return "sequence";
  if (mime?.startsWith("text/") || mime === "application/json" || mime === "application/yaml" || ext) return "code";
  return "unknown";
}
```

**mime 和扩展名在每个分支里并列出现，但 mime 写在前面。** 这个顺序不是随意的：

`metadata.mime` 来自**服务端**（上传时记录的类型、或探测类型），可信度高于扩展名。扩展名是用户自己起的，`model.pdb` 完全可以是个 PNG。**当两者冲突时，信服务端。**

对比一下"扩展名优先"会出什么问题：用户上传 `structure.pdb`，实际是 JSON 格式的结构描述——扩展名优先会用 PDB 解析器打开，解析失败，界面显示一堆乱码或空白。mime 优先会用 JSON 渲染器，用户至少能看到内容。

## 二、mime 的规范化：split(";", 1)

```typescript
const mime = metadata.mime?.split(";", 1)[0].toLowerCase();
```

两个动作：

**`split(";", 1)[0]`** —— mime 字符串经常带参数：`text/csv; charset=utf-8`、`text/plain;charset=ISO-8859-1`。`split(";", 1)` 取出主类型并丢弃参数。

**为什么不用 `startsWith`** —— `startsWith("text/")` 会把 `text/csv` 和 `text/xml` 都命中"文本"，但两者需要不同渲染器。而 `mime === "text/markdown"` 严格相等才能进 markdown 分支。

顺带的防御：`charset` 的分隔符可能是 `"; "`（带空格）或 `";charset="`（不带空格），`split(";", 1)` 两种都处理。

## 三、嗅探兜底：两条正则

结构文件这条分支最有意思：

```typescript
if (structureExtensions.has(ext) || /^(data_)?(entry|atom_site|struct)_/mu.test(sniff)) return "structure";
```

正则匹配的三个前缀：

| 正则片段 | 匹配 mmCIF 类别 |
|---|---|
| `data_` | `data_1ABC` —— mmCIF 文件开头的数据块名 |
| `entry_` | `entry.id` —— PDB 兼容块 |
| `atom_site_` | `atom_site.` / `atom_site_` —— mmCIF 的原子坐标表 |
| `struct_` | `struct_conf` —— 结构构象注释表 |

`m` 标志（multiline）让 `^` 能匹配每一行的行首——一个文件可能是 `data_` 开头但后面又有 `atom_site`，多行里任意一行命中就行。`u` 标志是 Unicode 模式。

**这些前缀都是 mmCIF 的保留类别名**，内容嗅探靠它们把无扩展名或错扩展名的结构文件识别出来。Mol* 导出的 `.cif`、转换工具吐出的随机文件名（比如 `output_001`），都能被这个正则捞回来。

序列那条更简单：

```typescript
if (sequenceExtensions.has(ext) || /^>[^\n]*/u.test(sniff.trim())) return "sequence";
```

**FASTA 的签名是行首的 `>`**。`sniff.trim()` 先去掉前导空行（某些工具会在文件开头加空行），然后 `/^>/` 只看第一个字符。

`[^\n]*` 而不是 `.*` —— 排除换行，确保匹配的是行首的那个 `>`，而不是文件中间某行恰好以 `>` 开头的普通文本。

## 四、扩展名集合：为什么一个都不漏

```typescript
const sequenceExtensions = new Set(["fa", "fasta", "faa", "fna", "a3m", "aln"]);
```

逐个看这些扩展名的生态：

- `fa` / `fasta` / `faa` / `fna` —— 蛋白/通用/蛋白氨基酸/核酸，四个不同生态的习惯写法
- `a3m` —— A3M 比对格式（Clustal Omega 的输出）
- `aln` —— 比对文件的通用约定

`imageExtensions` 里有 8 个：png/jpg/jpeg/gif/svg/webp/bmp/ico。`svg` 严格说不是位图，但要当图片渲染（不能当文本）。`ico` 经常被漏掉。

`molstarSceneExtensions` 只有 `mvsj`——Mol* 场景文件，专用 MIME `application/vnd.molstar.mvsj+json`。**厂商自定义 MIME 带 `vnd.` 前缀**是 IANA 的标准做法，这里既认 MIME 也认扩展名。

## 五、最后一行：`ext` 作为兜底

```typescript
if (mime?.startsWith("text/") || mime === "application/json" || mime === "application/yaml" || ext) return "code";
```

这是最宽松的分支：**只要有扩展名就用代码渲染器**。

因为代码渲染器是**万能降级方案**——它按文本 + 语法高亮显示任何东西。用户点开一个不知道是什么的文件，最差结果是一屏等宽字体的文本，至少能看出是不是二进制垃圾。

对比 `return "unknown"` 作为兜底：用户看到"无法预览"，什么信息都没有。**能显示出乱码也是有信息**（至少知道这不是可读文本）。

注意 `|| ext` 的位置——`ext` 是个字符串，`"noext" === ""` 时 `ext` 是 `"noext"`（split 的最后一个元素），真值。所以**任何带点的文件名都会落到 code 分支**。

对 truly 无扩展名的文件（`ext === ""`），且 mime 也不是文本，才落到 `unknown`。

## 六、languageForFilename：独立的语法映射

```typescript
export function languageForFilename(name: string): string {
  const ext = name.split(".").pop()?.toLowerCase() ?? "";
  if (ext === "yml" || ext === "yaml") return "yaml";
  if (ext === "md" || ext === "markdown") return "markdown";
  if (ext === "json") return "json";
  if (["sh", "bash", "zsh"].includes(ext)) return "bash";
  if (ext === "py") return "python";
  if (["js", "jsx", "mjs", "cjs"].includes(ext)) return "javascript";
  if (["ts", "tsx"].includes(ext)) return "typescript";
  if (ext === "sql") return "sql";
  return "text";
}
```

**注意它不复用 rendererKindFor 的结果**——两者是独立的判定：

- `rendererKindFor` 决定"用哪个渲染器"
- `languageForFilename` 决定"代码高亮用什么语言"

一个 `.pdb` 文件，`rendererKindFor` 返回 `"structure"`（3D 查看器），但如果用户想看纯文本，`languageForFilename` 返回 `"text"`——**PDB 的固定列宽布局，语法高亮帮不上忙还会误导**。

而 `.ts` 文件：`rendererKindFor` 返回 `"code"`，`languageForFilename` 返回 `"typescript"`。两个函数返回不同维度的东西，混用会出错。

sh/bash/zsh 三个都映射到 bash 高亮——高亮器支持 bash，shell 脚本的语法家族基本通用。

## 七、测试只有两条，但测的是关键分支

```typescript
describe("renderer registry", () => {
  it("prefers explicit MIME types and recognizes common bio formats", () => {
    expect(rendererKindFor({ name: "notes", path: "/workspace/notes", mime: "text/markdown" })).toBe("markdown");
    expect(rendererKindFor({ name: "alignment.a3m", path: "/workspace/alignment.a3m" })).toBe("sequence");
    expect(rendererKindFor({ name: "model", path: "/workspace/model" }, "data_entry_foo 1ABC")).toBe("structure");
  });

  it("falls back to code for a known text MIME", () => {
    expect(rendererKindFor({ name: "run.out", path: "/workspace/run.out", mime: "text/plain" })).toBe("code");
  });
});
```

三个用例覆盖了三种不同的判定来源：

1. **只有 mime，没有扩展名**（`notes`）→ mime 生效
2. **只有扩展名**（`alignment.a3m`）→ 扩展名生效
3. **只有内容**（`model` + `data_entry_foo` 开头）→ **嗅探生效**，这个例子无扩展名

注释说 `prefers explicit MIME types`——**"优先"这个词在第一个用例里其实没被真正验证**（因为没有冲突场景）。真正的优先级测试应该是 `{name: "a.cif", mime: "text/plain"}` 期望 `"code"`。这算是个测试覆盖上的缺口，不影响功能但值得记下。

## 八、总结

1. **mime 优先于扩展名**：服务端信息比用户命名的文件名可信
2. **mime 规范化**：`split(";", 1)[0]` 剥掉 charset 参数，严格相等才进特定分支
3. **嗅探兜底无扩展名文件**：mmCIF 类别名正则 + FASTA 的 `>` 行首
4. **code 是万能降级**：能显示乱码也是有信息，比"无法预览"强
5. **两个函数两个维度**：渲染器选择 vs 语法高亮语言，不复用
6. **扩展名集合要覆盖生态**：fa/fasta/faa/fna/a3m/aln、8 种图片格式

一句话：**类型分派的核心不是"猜对"，是"冲突时按可信度排序，猜错了还能降级"——每个分支都要有一条兜底路径。**
