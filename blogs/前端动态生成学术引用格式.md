# 绕开 APA 模板的版权问题：前端动态生成五种引用格式

学术产品几乎都要有"导出引用"功能。用户查一篇论文，顺手就要拷走 BibTeX 粘进 LaTeX，或者要一段 APA 格式贴进作业。

ScholarClub 就做了这个功能，支持五种格式。这篇记录一个具体的工程取舍：**为什么 APA 的格式是靠官方模板，而其他几种是我们自己带的。**

## 一、引用格式的本质是排版规则

先理解一下这件事的本质。不同引用格式（APA、MLA、Chicago...）的区别，**不是数据不同，而是排版规则不同**。

数据是一样的——作者、标题、期刊、年份、卷期页码。但每个格式对这些字段的排列顺序、标点、大小写、缩进规则都不一样。

比如同一个 2021 年的期刊文章：

- **APA**：`Smith, J. A. (2021). A study of things. Journal of Things, 12(3), 45-67.`
- **MLA**：`Smith, John A. "A Study of Things." Journal of Things, vol. 12, no. 3, 2021, pp. 45-67.`
- **Harvard**：`Smith, J. (2021) 'A study of things', Journal of Things, 12(3), pp. 45-67.`

字段一模一样，输出天差地别。

描述这套排版规则的标准叫 **CSL (Citation Style Language)**——用 XML 写一份规则文件，比如 APA 的规则大意是：

```xml
<citation>
  <layout prefix="(" suffix=")" delimiter="; ">
    <text variable="author"/>
    <text variable="year" prefix=", "/>
  </layout>
</citation>
```

有了 CSL 规则 + 一份文献数据，就能渲染出任意一种格式。这是纯规则驱动的，不需要为每个格式手写代码。

## 二、为什么不能直接打包所有官方模板

问题出在**许可证**。

CSL 官方模板仓库里的模板，每一份都有各自的许可声明，**不是统一的 MIT/CC 许可**。有些允许商业使用并有署名要求，有些明确限制了再分发。如果你的产品把全部分支都打包进前端 bundle 并对外提供服务，是有法律风险的。

ScholarClub 当时的取舍是：

| 格式 | 来源 | 原因 |
|---|---|---|
| BibTeX | citation-js 内置生成 | 本来就是程序生成的，不涉及模板许可 |
| APA | 官方模板 | 生态最通用，用户预期最高，值得承担署名义务 |
| MLA | **自带** | 公开可再分发的模板 |
| Harvard | **自带** | 同上 |
| Chicago | **自带** | 同上，而且我们用的是很老的版本（因为新版有许可限制） |

换句话说：**用户呼声最高、最常被引用的格式，值得承担许可成本；其余格式用可自由分发的模板覆盖。**

这不是纯技术问题，是产品判断。学术产品要为"大多数用户要的那个格式"负责，但不能为了全格式齐全把法务风险全揽过来。

## 三、运行时动态注册模板

citation-js 的 CSL 插件支持运行时注册自定义模板，这正是我们方案的关键。

```typescript
import { Cite, plugins } from '@citation-js/core';
import '@citation-js/plugin-bibtex';
import '@citation-js/plugin-csl';
import { chicago, harvard, mla } from './plugins';

const generateCitation = async (paper: MyObjectType, style: string) => {
  const citationData = {
    type: 'article-journal',
    id: paper.paperId || 'unknown-id',
    title: paper.title || 'Untitled',
    author: paper.authors?.map((author: { name: string }) => ({
      family: author.name.split(' ').slice(-1)[0] || 'Unknown',
      given: author.name.split(' ').slice(0, -1).join(' ') || 'Unknown',
    })) || [{ family: 'Unknown', given: 'Unknown' }],
    issued: {
      'date-parts': [[parseInt(paper.year) || new Date().getFullYear()]],
    },
    'container-title': paper.journal?.name || 'Unknown Journal',
    URL: paper.url || 'N/A',
    abstract: paper.abstract || 'No abstract available.',
  };

  const cite = new Cite(citationData);

  if (style === 'bibtex') {
    return cite.format('bibtex', { format: 'text' });
  }

  // 动态注册 CSL 模板
  const config = plugins.config.get('@csl');
  const templates: Record<string, string> = { harvard, mla, chicago };

  if (templates[style]) {
    config.templates.add(style, templates[style]);
  }

  return cite.format('bibliography', {
    format: 'text',
    template: style,
    lang: 'en-US',
  });
};
```

`config.templates.add(style, template)` 就是核心——把模板塞进插件配置，渲染时用 `template: style` 指定风格。BibTeX 走另一条路，因为它是程序直接生成的、不走 CSL。

## 四、数据映射的坑：作者名字怎么拆

这部分值得单独说，因为它是最容易出错的一环。

CSL 的作者数据不是字符串，而是结构化的 `{ family, given }`（姓、名）。而我们的数据库里通常只有一个姓名字符串。上面代码里：

```typescript
author: paper.authors?.map((author: { name: string }) => ({
  family: author.name.split(' ').slice(-1)[0] || 'Unknown',
  given: author.name.split(' ').slice(0, -1).join(' ') || 'Unknown',
}))
```

这里用了一个约定俗成的规则：**英文姓名最后一个单词是姓，其余是名**。所以 `John Adam Smith` → family=`Smith`，given=`John Adam`。

这在英文姓名里大致成立，但对以下情况会出错：

- **中国姓名**：`张三` / `李四` → 会被误判成 family=`张三`, given=`''`
- **复姓**：`欧阳修` → family=`修`, given=`欧阳`
- **带头衔**：`Dr. John Smith` → family=`Smith`, given=`Dr. John`（Dr. 被当名的一部分）

**更好的做法是数据入库时就拆好姓和名**，而不是在渲染时猜。如果你的数据源能提供结构化作者信息（比如从 Crossref / OpenAlex 拿），一定要用它们的结构化字段。这属于"在数据入口解决问题，不要在出口打补丁"。

## 五、字段缺失时的降级策略

学术数据的质量参差不齐，缺字段是常态。上面代码里几乎每个字段都带了默认值：

```typescript
type: 'article-journal',       // 固定按期刊文章渲染
id: paper.paperId || 'unknown-id',
title: paper.title || 'Untitled',
issued: {
  'date-parts': [[parseInt(paper.year) || new Date().getFullYear()]],
},
'container-title': paper.journal?.name || 'Unknown Journal',
URL: paper.url || 'N/A',
```

这个策略的原则是：**绝不让渲染因为缺字段而崩掉**。缺年份就用当前年，缺期刊就用占位符，缺 URL 用 `N/A`。

注意 `issued['date-parts']` 是二维数组——CSL 里日期支持"年 / 年-月 / 年-月-日"三种精度，所以年月日是数组的嵌套。

另一个取舍：`type` 固定成了 `'article-journal'`。但论文也可能是会议论文（`paper-conference`）、预印本（`article`）、书籍章节（`chapter`）……不同 type 在不同 CSL 格式下的排版差异很大（比如会议论文一般没有卷号）。如果你的产品要严谨，应该根据数据源判定 type 再映射，而不是一律当期刊文章。**这是当前实现的一个简化，学术规范性上不够严格。**

## 六、UI 层

渲染逻辑之外，UI 上要处理 Tab 切换、复制、下载。这些是标准 React 写法，但有两个小细节值得记一下。

**Tab 切换时重新生成**：不同格式对应不同渲染，每个 Tab 独立用 `CitationContent` 子组件包一层，各自维护 loading 状态：

```typescript
const [citation, setCitation] = useState('');
const [loading, setLoading] = useState(true);

useEffect(() => {
  const fetchCitation = async () => {
    setLoading(true);
    try {
      const citationText = await generateCitation(paper, format);
      setCitation(citationText);
    } finally {
      setLoading(false);
    }
  };
  fetchCitation();
}, [paper, format]);
```

**复制/下载直接读 DOM**：当前 Tab 的内容渲染在一个带 `id={format}` 的 textarea 里，复制和下载时直接从 `document.getElementById(activeTab)` 取值。这不是最优雅的做法（更 React 的方式是受控 state），但足够简洁，对这个场景也没问题。

## 结语

引用格式导出看着是个小功能，实际牵扯到**标准理解（CSL）、许可证边界、工程实现细节**三层。

核心的三个决策：

1. **用 CSL 规则引擎，而不是为每种格式手写代码**——可扩展，加新格式只是加个模板
2. **许可证决定了哪些格式自带、哪些走官方**——产品判断，不是技术判断
3. **数据质量决定输出质量**——作者姓名的拆分应该在入库时做好，而不是渲染时靠猜

这个功能在 ScholarClub 里不复杂，但它是一个很好的例子：**一个看似边缘的需求，答好它需要知道标准在哪、边界在哪、数据烂在哪。**
