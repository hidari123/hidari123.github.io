# 33 个领域技能包：把科学知识做成可替换的数据，不是代码

AtomOS 的 Agent 要懂蛋白质设计、结构预测、mRNA 疫苗——具体到会用 Boltz-2 预测结构、用 RFdiffusion 设计骨架、用 ESM2 做序列分析。

第一种做法是把它们写成 Agent 的内置工具：`predict_structure()`、`design_backbone()`……硬编码进循环。

**AtomOS 明确否决了这条路。** README 写着：

> 这些是可替换的领域知识，不是 Agent loop 中的固定流水线。科学软件通过 Project Shell、通用 Job、`/shared` 或批准的运行环境调用。

这篇讲这套 skill 系统的设计。

## 一、清单：33 个包，三层结构

`managed_skills/` 目录下有 33 个技能包，按用途分三层：

**入口/通用层**：

- `project-orientation`（项目导览）
- `job-submission-and-profiles`（作业提交规范）
- `job-diagnostics`（作业诊断）
- `scientific-software-discovery`（科学软件发现）
- `artifact-review`（产出物评审）

**领域工作流层**：

- `protein-design-common-workflow`（蛋白质设计通用流程）
- `biomolecular-target-research`（靶点研究）
- `mrna-vaccine-design` / `full-mrna-design` / `mrna-knowledge` / `mrna-evaluation`（mRNA 设计族）
- `cds-design` / `utr-design`（序列元件设计）

**软件专项层**（每个软件一个包）：

- `boltz-2-structure-prediction`、`boltzgen-protein-design-spec` / `boltzgen-protein-run-and-results`
- `rfdiffusion-protein-backbone-design`、`rfantibody-antibody-design`
- `esm2-model-usage`、`evo2-genomic-prediction`、`progen3-sequence-generation`
- `proteinmpnn-sequence-design`、`diffdock-protein-ligand-docking`
- `protenix-structure-prediction`、`openfold3-structure-prediction`
- `mmseqs2-sequence-search`、`rna-secondary-structure` / `vienna-rna-secondary-structure`
- `molstar-visualization`、`antibody-numbering-and-annotation`

**为什么专项软件不做成工具？** 因为科学软件的调用方式（参数、输入格式、结果解读）**本身就是知识**，且随版本漂移。RFdiffusion 换版本，命令行就变——写死在代码里就要发版，放数据包里改包就行。

## 二、Skill 的两个工具：加载与读文件

Agent 与 skill 的交互只有两个工具（catalogue 12 个工具里的 Skills/UI 组）：

```python
async def use_skill(...):        # 加载一个技能包
async def read_skill_file(...):  # 读取包内文件
```

`use_skill` 把包的主说明注入上下文——Agent 从此"知道"这个领域怎么干。`read_skill_file` 按需读包内的具体文件（脚本、参考、模板）。

`read_skill_file` 有个明确的尺寸约束：

```python
MAX_FILE_CHARS = 64 * 1024
# ...
"content": file.content.decode("utf-8-sig")[:MAX_FILE_CHARS],
```

**64K 字符截断**。这是上下文经济学：skill 包里可能有很长的参考文档、大段脚本，全部注入会挤爆窗口。截断保证单次读取的预算上限，Agent 需要更多内容时分段读。

顺带的细节：`decode("utf-8-sig")`——**剥掉 BOM 再解码**。Windows 环境编辑过的文件常带 BOM，不剥的话第一个字符就是 `\ufeff`，注入 prompt 后是个看不见的污染。

## 三、发现链：Agent 怎么知道该用哪个包

`scientific-software-discovery` 这个包本身就是设计巧思——**"怎么发现可用软件"这件事本身也被做成了技能**。

Agent 收到"帮我预测这个结构"时，不需要预先知道 Boltz-2 存在。它的推理路径：

1. 领域包（如 `protein-design-common-workflow`）里写着"结构预测是常见步骤，具体软件见 discovery 流程"
2. Agent 调 `use_skill("scientific-software-discovery")`，学会怎么探测环境里的软件
3. 通过 `bash_run` 探测 `/shared` 里装了什么
4. 加载对应软件专项包（如 `boltz-2-structure-prediction`），获得调用知识
5. `submit_job` 提交执行

**知识的获取是渐进的、按需的**——不是把 33 个包全塞进上下文。每一步只加载下一步需要的。

## 四、包的内容形态

一个 skill 包里有什么？以 `molstar-visualization` 为例（含 60KB 的 `compile_molstar_scene.py` 脚本）、`mrna-artifact-workspace`（含 51KB 的 `runner.py`）：

```
managed_skills/<name>/
  ├── SKILL.md          # 主说明（use_skill 注入的就是它）
  ├── scripts/          # 可执行脚本（read_skill_file 读取后可用）
  └── references/       # 参考资料
```

**说明是 markdown，脚本是代码，参考是数据**——包的形态天然分层。Agent 读 SKILL.md 获得决策知识，需要执行时读脚本、通过通用执行工具跑。

脚本本身**不直接执行**——Agent 读懂它、（必要时）修改它、然后通过 `bash_run` / `submit_job` 走通用执行路径。**skill 提供知识，执行走通用通道，两者解耦。**

## 五、可替换性的工程含义

"可替换"不是修辞，是运维属性：

- **升级软件**：改对应包，不动平台代码
- **下线软件**：禁用包即可，Agent 的其他能力不受影响
- **私有流程**：研究所自己的管线写成私有包，不污染开源主库
- **版本共存**：同一软件多版本知识可以并存成多个包

管理面（Admin → Skills）支持对包做启用/禁用/更新——`skills` / `skill_package_revisions` / `skill_package_files` 三张表支撑版本化，每个包的修订历史可追溯。

## 六、为什么这是"正确的分层"

把这套设计和"工具硬编码"对比：

| 维度 | 硬编码工具 | 数据化 skill |
|---|---|---|
| 新增领域能力 | 发版 | 加包 |
| 软件升级 | 改代码、测试、发版 | 改包内容 |
| 上下文成本 | 全部工具 schema 常驻 | 按需加载 |
| 循环复杂度 | 工具越多越臃肿 | 循环恒定 12 个工具 |
| 领域专家贡献 | 必须会写代码 | 写 markdown 就行 |

最后一行是隐藏收益：**领域专家（生物学家、化学家）不会写代码，但会写文档**。skill 包把"领域知识"的作者群从工程师扩大到了科学家——这比任何技术优化都值钱。

Agent 循环本身只有 12 个工具：5 执行 + 3 技能/UI + 4 记忆。**引擎极简，知识外置**——这个分层的边界划在了"变化频率"上：循环几乎不变，知识天天变。

## 七、总结

1. **知识是数据不是代码**：33 个包按需加载，平台循环恒定 12 工具
2. **两个工具管全部技能**：`use_skill` 注入知识、`read_skill_file` 按需读文件
3. **64K 截断 + BOM 剥离**：上下文预算和编码卫生都是显式工程
4. **发现也是技能**：`scientific-software-discovery` 让"知道有什么可用"变成可学习的知识
5. **分层边界划在变化频率上**：引擎不变、知识常变、执行通用

一句话：**Agent 的聪明程度不取决于内置了多少工具，而取决于"按需获得正确知识"的通道有多顺畅。**
